## 1. One refused replace generates `OrderModifyRejected` twice when both Alpaca channels report it, and the test that covers the stream channel cannot tell the channels apart or see the duplicate

- **File / function:** `packages/canon-alpaca/src/canon_alpaca/execution.py`, `_modify_order` / `_replace_refused` (line 980) and `_apply`, `order_replace_rejected` branch (line 1232); test `test_replace_rejected_on_the_stream_is_modify_rejected` in `packages/canon-alpaca/tests/test_execution_client.py:1019`; stand-in in `packages/canon-alpaca/tests/conftest.py`, `FakeOrdersClient.replace_order_by_id` (line 446).
- **What goes wrong:** The client generates `OrderModifyRejected` from the HTTP 422 path (`_replace_refused`) and again, with no deduplication or pending-modify tracking, from the stream's `order_replace_rejected` (`_apply` line 1232). Unlike `_reject` for submits, which is guarded by `self._finished`, nothing suppresses the second generation, so a strategy receives two `OrderModifyRejected` events for one modify command. The stand-in models exactly that combined behaviour: with `replace_script == "reject"` it both sends `order_replace_rejected` on the stream and raises a 422. The test then asserts only `"OrderModifyRejected" in strategy.names()`, so (a) it passes on the HTTP path alone if the stream branch is deleted or broken, despite its name claiming to test the stream, and (b) it passes with one, two, or more rejections.
- **Shown by:** Probe (copied harness, printed inside the test): `STREAM_REJECT_EVENTS ['OrderSubmitted', 'OrderAccepted', 'OrderPendingUpdate', 'OrderModifyRejected', 'OrderModifyRejected']` for the unmodified `test_replace_rejected_on_the_stream_is_modify_rejected` scenario. Whether real Alpaca sends both signals for one refusal is `UNVERIFIED` (ADR 0036 itself lists `order_replace_rejected` as shown by no run), but the client's own stand-in asserts that combined model and the client emits the event twice under it.

## 2. A replacement's `rejected` arriving after the old order's fill is silently dropped, contradicting the new documentation, and its test asserts only that it was not an `OrderRejected`

- **File / function:** `packages/canon-alpaca/src/canon_alpaca/execution.py`, `_apply` (finished-order guard at line 1223, before the `rejected`-of-a-replacement branch at line 1243); test `test_rejected_replacement_is_modify_rejected_not_order_rejected` in `packages/canon-alpaca/tests/test_execution_client.py:1030`; statements in `execution.py` header (lines 25–26), `packages/canon-alpaca/README.md` Modify bullet, and ADR 0036 Modify section ("`order_replace_rejected` and the `rejected` of a replacement that has not taken over are `OrderModifyRejected` too").
- **What goes wrong:** `_apply` returns early when the node's client order ID is in `self._finished`. A `fill` for the old order adds it there (line 1278). So in precisely the race the new code comment describes — old order fills first, replacement is then rejected — the replacement's `rejected` never reaches the branch at line 1243 and no `OrderModifyRejected` is generated. That may or may not be the right event-model choice for a filled order, but it makes the unqualified statements in the header, README, and ADR false for this sequence, and the test named "is modify rejected" never asserts a modify rejection: it asserts only `"OrderRejected" not in strategy.names()` and `"OrderFilled" in strategy.names()`, both of which also hold if the `rejected` update is dropped entirely (e.g. if the branch at line 1243 is deleted).
- **Shown by:** Probe (copied harness, printed inside the test's own fill-then-rejected sequence): `REJECTED_REPLACEMENT_EVENTS ['OrderSubmitted', 'OrderAccepted', 'OrderPendingUpdate', 'OrderFilled']` — no `OrderModifyRejected`, test still passes.

## 3. (Unsure) The stored PATCH answer can be left behind in `_answers` when the `replaced` update is applied before `_modify_order` resumes

- **File / function:** `packages/canon-alpaca/src/canon_alpaca/execution.py`, `_modify_order` (answer stored at line 977, after the awaited PATCH returns) and `_replaced` (answer popped at line 1292).
- **What goes wrong:** `_replaced` pops `_answers[str(old.replaced_by)]` only at the moment it starts. If the stream's `replaced` is applied (queue consumer task) in the window between Alpaca taking the replace and `_modify_order` regaining the loop after its shielded worker-thread call, `_replaced` finds no answer, fetches the replacement by ID (correct `OrderUpdated`), and then `_modify_order` stores the answer under that replacement ID with nothing left to pop it. The entry then survives until disconnect (or an `order_replace_rejected` cleanup), one retained `AlpacaOrder` per such modify, and a duplicate/replayed `replaced` for the old order would pop the stale entry and emit a second, stale `OrderUpdated` for a replacement that may already have been replaced again. I am unsure this interleaving is reachable in practice: it depends on the stream thread's hand-off beating the PATCH call's completion callbacks. In two probe runs (normal timing, and with the stand-in's PATCH return delayed) `client._answers` was empty after a completed modify, so I did not reproduce it; I report it as a code-reading risk, not an observed failure.

## 4. A `replaces` chain longer than `MAX_REPLACE_CHAIN` is the one "miss" that is not cached, so every later update or report for that order repeats up to 16 Alpaca lookups ahead of the node's own updates

- **File / function:** `packages/canon-alpaca/src/canon_alpaca/execution.py`, `_node_order_id` (lines 1165–1212, the post-loop warning/return at lines 1207–1212); ADR 0036 ("traced … cached, misses too").
- **What goes wrong:** Both other negative outcomes are memoised in `self._foreign` (no `replaces` link, line 1185; 404 on a link, line 1193), but the chain-too-long outcome returns `None` without recording anything. Because trade updates are applied by one in-order consumer task, each subsequent update for such an order (and each bulk report that reaches it) re-walks up to 16 `get_order_by_id` calls while holding up later updates, including fills for the node's own orders queued behind it. It also makes the ADR's "misses too" caching claim false for this case. Shown by code reading; no test exercises a >16 chain.

## 5. (Unsure) A single-order status report that must follow a `replaced` link fails outright if the replacement cannot be read, unlike every neighbouring lookup

- **File / function:** `packages/canon-alpaca/src/canon_alpaca/execution.py`, `_order_status_report` (lines 1405–1435, follow-the-chain loop at lines 1423–1430).
- **What goes wrong:** The initial `get_order_by_id` / `get_order_by_client_id` 404 returns `None` (lines 1419–1422), and tracing failures inside `_order_report` are caught and degrade to "not reported" with a warning (lines 1506–1513), but the loop that follows `replaced_by` calls `get_order_by_id` with no error handling: a 404/`APIError`/`OSError` there propagates through `_logged` and fails the whole report request (and with it a reconciliation pass) instead of settling that one order. The same situation in `_replaced` is deliberately degraded to "no `OrderUpdated`, reconciliation settles it". I am unsure whether failing the request is intended — it is visible and logged, not silent — but it is inconsistent with the three adjacent decisions, and no test covers a report whose `replaced_by` target is unreadable (the existing unreadable-replacement test covers only the stream path). Shown by code reading only.

## 6. Bulk reconciliation logs a false "not in this slice" warning for every `replaced` order it correctly skips

- **File / function:** `packages/canon-alpaca/src/canon_alpaca/execution.py`, `_order_report` (lines 1500–1540, warning at lines 1536–1540) with `order_status_report` raising/returning `None` for `REPLACED` (lines 505–507).
- **What goes wrong:** `order_status_report` returns `None` for a `replaced` order by design ("its replacement is reported instead"), but `_order_report` treats every `None` as an unmappable order and logs `Alpaca order … (…, replaced) is not reported: its type, side, class, quantity or time in force is not in this slice`. After this commit, `replaced` orders are a normal, expected member of any non-open-only `get_orders` result, so each reconciliation that includes one emits a warning naming a wrong reason. Shown by code reading; the reconciliation test at `test_execution_client.py:971` includes a replaced order in the bulk result and does not assert on this log.

## 8. (Unsure) The cancel-of-a-just-replaced-order redirect has no offline test that can fail, and the stand-in cancels a replaced order as if nothing happened

- **File / function:** `packages/canon-alpaca/src/canon_alpaca/execution.py`, `_cancel_refused` redirect (lines 911–918, added by this commit); `packages/canon-alpaca/tests/conftest.py`, `FakeOrdersClient.cancel_order_by_id` (line 428).
- **What goes wrong:** The redirect fires only when a cancel of the old venue order ID is refused 422 and Alpaca shows it `REPLACED`. The stand-in's cancel does not refuse a `replaced` order at all: it sends a `canceled` update for the old order dict. So no offline test exercises the branch (deleting it changes no offline outcome), an offline test of "cancel the old ID after a replace" would pass for the wrong reason (cancel accepted under the dead ID), and the paper cancel test cancels only after `OrderUpdated` has already moved the node's venue order ID to the replacement, so it does not exercise the redirect either. Whether Alpaca actually answers a cancel of a replaced order with 422 (rather than 404 or 204) is `UNVERIFIED` in the commit's own evidence; if it answers anything else, `_cancel` logs "no definitive answer" and the replacement is never canceled. I am unsure the branch is wrong — the code is plausible against "Delete Order by ID"'s 422 wording — but as committed it is an untested guess carrying a real order-cancel path.
