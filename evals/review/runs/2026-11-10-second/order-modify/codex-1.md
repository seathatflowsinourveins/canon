# Review of `3a00f617fd20c97d647ee51f7c2c4091aac3a035`

Paths below are relative to `packages/canon-alpaca/`. Findings are ordered by severity.

1. **Reconciliation drops real fills and terminal states on a successful replacement.** `src/canon_alpaca/execution.py:1515–1524`, `_order_report`. If A is replaced by B while the node is disconnected or misses the `replaced` message, its cached venue ID can still be A. When B fills, is canceled, or expires before reconciliation, the guard discards B because it is closed and its venue ID differs from the cache. The same reconciliation skips A because A has status `replaced`. A single-order query that follows A's `replaced_by` link hits the same guard. An offline call to `_order_report` with B filled, a resolved ancestry and A cached returned `None`.

2. **A transient ancestry lookup error hides an open order from reconciliation.** `src/canon_alpaca/execution.py:1505–1514`. With a cold map, an open replacement B can be present in the orders response while A, its predecessor, is outside the response window. If looking up A returns 504 or raises a connection error, the bulk report silently omits B apart from a warning and can appear successful with no report of the working order. This also bypasses the adapter's error on an unrepresentable open order. An offline call with a simulated ancestry 504 and B in `new` returned `None`.

3. **A replacement lookup can stop delivery of fills for every order.** `src/canon_alpaca/execution.py:1141–1152,1185,1295,1361–1363`. For example, the first post-restart update belongs to a replacement and the HTTP read of its predecessor stalls. The only consumer awaits the lookup, alpaca-py's REST call has no HTTP timeout, and later stream fills and cancels for unrelated orders sit in the unbounded queue. Before this change those unrelated trade updates needed no REST call to be applied. Verified by tracing the consumer, queue and pinned client's timeout behavior.

4. **Restart during an in-flight replace can fail order reconciliation.** `src/canon_alpaca/execution.py:272–279,504–511,1470–1476`. The pinned SDK exposes `pending_replace` as an order status, but the adapter can now put an order into that state and cannot report it. If reconciliation reads A before the replacement has settled, the status is treated as an unmapped open order and raises. An offline call to `order_status_report` with that status raised `ValueError` for an open order.

5. **The documented fill-then-reject race drops the modify rejection.** `src/canon_alpaca/execution.py:1223–1224,1243–1253,1277–1278`. When A fills before B takes over, A's fill puts the shared client ID in `_finished`. B's later `rejected` is discarded before the code intended to emit `OrderModifyRejected`. An offline call with that shared ID in `_finished` emitted zero modify rejections. `tests/test_execution_client.py:1030–1051` explicitly sends this sequence, then checks only that the original filled and was never rejected, so it passes with the promised modify rejection absent.

6. **A delayed replacement confirmation can move the local order backward.** `src/canon_alpaca/execution.py:1228–1230,1280–1321`. After A→B→C, a duplicate or delayed `replaced` message for A resolves to the same local order and can generate a fresh `OrderUpdated` with B's venue ID and terms. The code checks neither that A is the current venue ID nor that this transition has already been applied. If B is already marked `replaced` and there is no cached answer, the report conversion instead refuses it. The rollback is possible with a cached B answer or a lookup that still sees B as open. Static finding. Paper delivery of replayed messages and the downstream handling of the stale event are unverified.

7. **A failed confirmation lookup can discard a valid update, or the answer can be stranded.** `src/canon_alpaca/execution.py:962–978,1292–1305`. REST lock release is posted from the worker before the PATCH coroutine necessarily resumes and stores the answer. The stream consumer can observe no answer, queue its own GET, then fail that GET even as the valid PATCH answer arrives. It logs that no update was applied and never revisits the stored answer. The reverse race also permits the consumer to process the replacement via GET before the command stores the now-unused answer. A successful PATCH followed by a replacement rejection similarly leaves its stored answer behind on the `rejected` branch. Static interleaving analysis.

8. **Long chains lose order identity after a cold restart.** `src/canon_alpaca/execution.py:1176–1211,1419–1433`. Seventeen sequential accepted amendments are allowed while the in-memory map is warm. If only the original order is held after a restart, an update for the seventeenth successor cannot reach it and is dropped as foreign. Bulk reconciliation can report the successor under Alpaca's generated ID. A single report query for the original can stop on an intermediate `replaced` record and return no report. The 16-link bound is explicit in ADR 0036. Its consequences follow from the two traversal loops, and the adapter does not apply a corresponding limit to successive modifications.

9. **A 422 during the pending phase can reject an amendment that later succeeds.** `src/canon_alpaca/execution.py:987–1020`. If the first PATCH was taken, the SDK retries after a 504, and the retry receives a 422 while the first request is still pending, the read sees `pending_replace`. The code emits a definitive rejection and a subsequent `replaced` emits an update for the same attempt. This sequence is conditional. A 422 for this particular pending retry is unverified on paper. A separate ambiguity exists even after completion because comparing only the requested terms cannot distinguish another actor's same-terms replacement from a retry of this command.

10. **The direct paper test can leave open orders or an unintended position.** `tests/test_paper_replace.py:99–145,149–161,185–209`. It tracks order IDs only after successful REST replies. A submit or replace that takes effect but loses its reply leaves an ID untracked. A replaced A is considered closed, and cleanup never follows A's `replaced_by` to the live B. The hard-coded open set also treats any unlisted status as closed. Cleanup counts buys only from received stream messages. A missed fill can let the test pass and leave the bought share, and duplicate fill messages can cause an oversell. Even when the fill is correctly counted, the cleanup submits a sell without checking it fills before asserting the shares “were sold back.” These are static failure sequences. They also invalidate the unconditional cleanup claim in the new test's header and README table.

11. **The adapter paper success test can try the amendment before the order is replaceable.** `tests/test_paper_execution.py:127–134,166–188`. The strategy PATCHes on its first NautilusTrader `OrderAccepted`. The adapter can emit that from the submit reply, or from Alpaca's `accepted` or `pending_new`, before Alpaca's `new`. The commit's own execution header and direct paper test identify `accepted` as unreplaceable, and the direct test waits for `new`. When routing lags the first acknowledgement, this test can fail even if the adapter correctly handles the refusal. Verified the event path by inspection.

12. **The offline stream-rejection test passes when the stream rejection handler is disabled.** `tests/conftest.py:480–482` and `tests/test_execution_client.py:1019–1027`. The stand-in sends `order_replace_rejected` and also raises HTTP 422. The test requires only that a modify rejection appear, so the REST handler alone can satisfy it. I reran this test with an in-memory monkeypatch that ignored every `order_replace_rejected` update. It still passed. The dual response also creates two attempts to emit a rejection in this test setup, with no assertion that there is exactly one.

13. **The direct paper test can fail because the stream has yet to deliver its confirmation.** `tests/test_paper_replace.py:178–195,220–228`. It uses a fixed delay after `listen` and a fixed three-second grace before stopping the stream. REST status can already show the replace completed while its stream message is delayed. A confirmation arriving after the grace period yields an empty list and fails the assertion. Static finding. The paper timing was unverified.

14. **The documentation gives conflicting event and refusal behavior.** `README.md:205–214,254–256` and `src/canon_alpaca/execution.py:17–28`. The Stream section still lists `replaced` as an unmapped warning although the new dispatch branch uses it to emit `OrderUpdated`. The new Modify section describes Alpaca refusals categorically as `OrderModifyRejected` although non-422 errors, lookup failures after a 422, and matching already-replaced responses follow other paths. The header's categorical replacement rejection also conflicts with the fill-first sequence in finding 5. The README's unconditional `DEFAULT` stop trigger type at lines 201–203 conflicts with the now-documented path preserving a cached order's `LAST_PRICE` trigger type.

Paper behavior and other upstream behavior marked unverified require evidence outside this review. The checkout was left unchanged.
