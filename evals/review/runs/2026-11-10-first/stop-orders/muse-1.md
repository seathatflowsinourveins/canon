# Review of commit 724246e85ed29d138cd1e5d3af7e2c3cc6d4840b in packages/canon-alpaca/

Scope: `git diff 724246e85ed29d138cd1e5d3af7e2c3cc6d4840b^ 724246e85ed29d138cd1e5d3af7e2c3cc6d4840b` in `packages/canon-alpaca/` (market/limit execution extended to stop and stop-limit orders). Offline verification run: `mise exec -- uv run --locked pytest packages/canon-alpaca/tests/test_execution_client.py -q` — 50 passed; plus `test_upstream_contract.py` and `test_parsing.py` — 129 passed in total across the three files. Paper tests were not run (they need a key). Probes below were written under `/tmp` and run against the offline test harness in `packages/canon-alpaca/tests/` (real `LiveNode`, fake venue in `tests/conftest.py`); the checkout was not modified (`git status` clean).

Defects, most severe first:

## 1. Stop-market order with `display_qty` is sent to Alpaca with the display quantity silently dropped, instead of being denied

- File/function: `packages/canon-alpaca/src/canon_alpaca/execution.py`, `AlpacaExecutionClient._denial` (lines 879–894) and `AlpacaExecutionClient._order_request` (lines 897–915).
- What goes wrong: the display-quantity denial is inside the `if order.order_type in LIMIT_PRICED:` branch (`LIMIT_PRICED = {LIMIT, STOP_LIMIT}`, line 237), so it covers limit and stop-limit but not stop-market. A stop-market order is the only other supported type that carries `display_qty` (NautilusTrader's `StopMarketOrder` and the `OrderFactory.stop_market(..., display_qty=...)` parameter both expose it; a limit order with `display_qty` is denied by the same code, and the new README text at `packages/canon-alpaca/README.md:197` and the header at `execution.py:71` state flatly that display-quantity orders are denied). For a stop-market order `_denial` returns `None`, and `_order_request` builds a `StopOrderRequest` with no display field (alpaca-py's request classes have none), so the full quantity is sent as a plain stop. The user asked for an iceberg showing only the display quantity; Alpaca receives and will execute against the whole quantity as one stop order.
- How I showed it: (a) direct probe — built an `AlpacaExecutionClient` shell with a stub provider holding a tradable `Equity`, called `_denial` on an order object with `order_type=STOP_MARKET, display_qty=Quantity(1)`: it returned `None`, and `_order_request` produced a plain `StopOrderRequest(stop_price=200.0)`; the equivalent limit and stop-limit objects returned `"display quantity is not supported"`. (b) real-node probe (`/tmp/test_probe_disp4.py`, reusing the harness in `tests/test_execution_client.py`): a strategy submitted `order_factory.stop_market(AAPL, BUY, 2, Price("200.00"), display_qty=Quantity(1), GTC)` on the first quote; events were `OrderSubmitted, OrderAccepted, OrderFilled` and the fake venue recorded one submitted `StopOrderRequest` — no `OrderDenied`. The control probe with `order_factory.limit(..., display_qty=Quantity(1))` produced `OrderDenied: display quantity is not supported` and nothing submitted, confirming the limit branch (and that engine/factory pass `display_qty` orders through to this client).

## 2. Stop and stop-limit orders naming a different `trigger_instrument_id` are sent to Alpaca, which triggers them on the order's own symbol

- File/function: `packages/canon-alpaca/src/canon_alpaca/execution.py`, `AlpacaExecutionClient._denial` (lines 849–894, never reads `trigger_instrument_id`) and `_order_request` (lines 897–915).
- What goes wrong: NautilusTrader's `StopMarketOrder`/`StopLimitOrder` (and `OrderFactory.stop_market`/`stop_limit`) accept `trigger_instrument_id`, the instrument whose price elections are meant to watch. Alpaca's `StopOrderRequest`/`StopLimitOrderRequest` have no such field — a stop is elected on the traded symbol itself ("elected on the consolidated print", `execution.py:62–63`). The client neither denies such an order nor maps the field, so an order written to trigger AAPL off, say, MSFT prints is submitted to Alpaca as an ordinary AAPL stop and triggers on AAPL. That is a silently different order from the one the strategy constructed, in the same class as the trigger-type denial the change does implement (lines 879–884).
- How I showed it: the same stub probe as in 1 — a `STOP_MARKET` and a `STOP_LIMIT` order object with `trigger_instrument_id=MSFT.ALPACA` both got `_denial(...) is None` and were turned into AAPL `StopOrderRequest`/`StopLimitOrderRequest`s. Real-node probe (`/tmp/test_probe_disp5.py`): `order_factory.stop_market(AAPL, BUY, 2, Price("200.00"), trigger_instrument_id=MSFT.ALPACA)` was created with `trigger_instrument_id=MSFT.ALPACA`, then events were `OrderSubmitted, OrderAccepted, OrderFilled` with one request submitted to the fake venue — no denial. (I did not re-probe stop-limit through the node; the code path is identical: `_denial` checks only `trigger_type`/`trigger_price`/`price` for stop types, and `_order_request` only forwards `symbol`/`qty`/`side`/`time_in_force`/prices.)

## 3. (Unsure) An open stop in an Alpaca status outside `OPEN_STATUSES` fails start-up reconciliation, although the change presents open stops as reportable

- File/function: `packages/canon-alpaca/src/canon_alpaca/execution.py`, `order_status_report` (lines 444–507) with `OPEN_STATUSES` (lines 243–249, unchanged by this commit).
- What goes wrong, if the premise holds: `_order_report`/`order_status_report` raise `ValueError("... is open with status ...")` for any open Alpaca order whose status is not `new`, `accepted`, `pending_new`, `partially_filled` or `pending_cancel` (closed statuses aside). alpaca-py's `OrderStatus` also has `held`, `accepted_for_bidding`, `calculated`, `stopped`, `suspended` and `done_for_day`. If Alpaca leaves a resting or elected stop in one of those (I could not verify offline which status a resting stop carries, and the repo's own ADR 0036 marks an elected stop's stream behaviour `UNVERIFIED`), start-up reconciliation now fails on an ordinary working stop — a failure mode stop orders newly expose, since this commit's README/header say open stops are reported (`README.md:202–203`, `execution.py:101–103`) with only the type/side/class/quantity/time-in-force limits named there. I am unsure this is a defect: the pre-existing "Known limits" at `execution.py:93–95` does say an order whose status this slice does not map fails the report when open, so the behaviour may be intended fail-closed design; it is a defect only if a normally-resting stop actually arrives in one of those statuses.
- How I showed the mechanism (not the premise): unit probe (`/tmp/probe_report.py`) calling `order_status_report` on alpaca-py `Order`s built from the `tests/conftest.py` docs payload — an open stop (`type=stop, stop_price="140.5"`) with status `accepted` reported as `STOP_MARKET/ACCEPTED` with trigger `140.5000/DEFAULT`, while the same order with status `held`, `accepted_for_bidding` or `calculated` each raised `ValueError: Alpaca order ... is open with status held` (etc.). Filled stop and stop-limit orders reported correctly (`FILLED`, both prices).

## 4. Documentation overstates the report's trigger type: an open stop held by the node with `LAST_PRICE` is not reported as `DEFAULT`

- Files: `packages/canon-alpaca/README.md:202–203` ("An open stop is reported with its stop price as trigger price and trigger type `DEFAULT`") and `packages/canon-alpaca/src/canon_alpaca/execution.py:101–103` (same sentence in "Known limits"), against `AlpacaExecutionClient._order_report` (lines 1157–1164) and `order_status_report` (lines 497–499).
- What goes wrong: the statements are unconditional, but `_order_report` — the method reconciliation actually calls — patches the report with the held order's trigger type: `held.trigger_type if held is not None and held.order_type in STOP_TYPES else None`, and `order_status_report` uses `trigger_type or TriggerType.DEFAULT`. So any mass/single status report for a stop this node submitted with `TriggerType.LAST_PRICE` (which `_denial` accepts and the offline test `test_stop_order_is_sent_with_its_stop_price_and_fills` submits) carries `LAST_PRICE`, not `DEFAULT`. `DEFAULT` appears only when the node does not hold the order (e.g. start-up reconciliation of an order placed before the window). A reader relying on the README/header — the repo treats these records as the statement of behaviour — would mis-predict what reconciliation delivers for the common held-order case. This is the correct behaviour with the wrong description, not the reverse; `order_status_report`'s own docstring (lines 451–452) states it correctly, which makes the summary sentences the false ones.
- How I showed it: read-only — the three code locations above plus the accepting test; no run needed, since `_order_report` passes `held.trigger_type` straight through and the offline stop test already exercises a held `LAST_PRICE` stop through submit.

## 5. The new paper test for "the client's report" bypasses the client method it claims to check, so it can pass while that method is wrong

- File: `packages/canon-alpaca/tests/test_paper_execution.py`, `test_paper_stop_buy_is_accepted_with_its_prices` (the `check` callback and the assertions after `run_exec_tester`), with docstring lines claiming "the client's report of Alpaca's order (what reconciliation reads) has the same type, prices and trigger type `DEFAULT`".
- What goes wrong: the test never calls the client's report path. It calls the module-level `order_status_report(held, 0)` directly, without the `trigger_type` argument, so for any stop order that function returns `TriggerType.DEFAULT` by construction (execution.py lines 497–499) regardless of what the node's order holds or what `AlpacaExecutionClient._order_report` (lines 1157–1164) would produce. The trigger-type assertion therefore cannot fail for the reason the docstring gives: if `_order_report` dropped the trigger price, returned the wrong trigger type, or raised on a held stop, this test would still pass, provided the bare function maps the Alpaca payload. It also passes `ts_init=0`, a timestamp no real report carries. (The prices assertions are not affected — `order_status_report` is genuinely the function that maps them — and upstream `ExecTester`'s default `stop_trigger_type` is `DEFAULT`, verified below, so the asserted value happens to be the node's too; the defect is that the test does not show it.) This is a paper-only test, so it cannot be run here; by inspection it would also not catch a regression in `_order_report`'s cache patch in the offline suite's place, since the offline startup test (`test_startup_reconciliation_reports_open_stop_orders`) only exercises the not-held branch.
- How I showed it: read the test and `order_status_report`/`_order_report` as above; and ran `.venv/bin/python -c` constructing a default `ExecTesterConfig`, which printed `stop_trigger_type DEFAULT` — confirming the expected value coincides with, rather than is proven by, the direct call.

## Notes on what was checked and found sound

- `_order_request` maps stop-limit fields in the right order (`stop_price=trigger_price`, `limit_price=price`), sends `DAY`/`GTC` only, and never sets `extended_hours` (alpaca-py's default is `None`, as the offline stop-limit test asserts); `order_status_report` emits `price` only for `LIMIT_PRICED`, `trigger_price`/`trigger_type` only for stop types, and the new `exact_report_price` `None` guard turns a missing limit/stop price on an open order into a start-up failure rather than a `decimal.InvalidOperation` escaping the `except ValueError`.
- The offline tests added or changed by the commit (stop submitted and filled for `trigger_type` `None`/`DEFAULT`/`LAST_PRICE`, stop-limit submitted and cancelled, denials for trailing type, `FOK`, `BID_ASK`/`MARK_PRICE` trigger types, sub-penny stop and limit prices, post-only stop-limit, startup reconciliation of open stop/stop-limit, trailing-stop failing startup) all pass, and a probe reconciling a *filled* stop at startup produced a `FILLED STOP_MARKET` order and the matching position.
- The statement at `README.md` (and `execution.py:68`) that Alpaca sends no election update, so no `OrderTriggered` is generated, is presented as settled fact while ADR 0036 records what Alpaca's stream sends on election as `UNVERIFIED`. I list this as an observation, not a counted defect: the wording in `execution.py` is about what Alpaca *documents*, and ignoring any such update has the same observable outcome the text describes.
