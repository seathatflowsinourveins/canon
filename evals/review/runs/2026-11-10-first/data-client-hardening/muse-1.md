## Defects, most severe first

### 1. An abandoned stream can emit duplicate or stale quotes and trades after a reconnect

- **Where:** `packages/canon-alpaca/src/canon_alpaca/data.py`, `_on_quote`, `_on_trade`, `_on_trade_cancel`, `_on_trade_correction` (lines 688–702), feeding `_emit_quote` and `_emit_trade` (lines 623–658); compare `_on_stream_exit` (lines 679–684).
- **What goes wrong:** The stream-exit report is guarded by stream identity (`stream is self._stream`), but data messages are not. The handlers registered on a stream carry no identity of which stream delivered them: they only post the message to the node's loop, and `_emit_quote`/`_emit_trade` then check only `self._stopping` and membership of the symbol in `self._quote_symbols`/`self._trade_symbols`. After a timed-out `_disconnect`, the old stream and its thread are explicitly left running with its alpaca-py handlers still registered (lines 467–481 and the `STREAM_JOIN_TIMEOUT_SECS` note, lines 136–146). A reconnect sets `_stopping = False`, points `_owner_loop` at the (same) node loop again and rebuilds the symbol sets. From then on the abandoned stream satisfies every check a live stream satisfies.
- **Sequence that shows it:** Subscribe to AAPL quotes on stream A; call `_disconnect` with the stream ignoring `stop()` so it times out and raises while A stays alive; `_connect` again and subscribe to AAPL quotes on the new stream B (AAPL is now back in `_quote_symbols` and `_stopping` is False); A now delivers an AAPL quote through the `weak_coroutine(self._on_quote)` it still holds. The quote is posted to the node's loop and emitted exactly as if B had delivered it, so the strategy and cache can receive a duplicate, or an older quote from A after a newer one from B. The same applies to trades, trade cancels and trade corrections. I showed this by reading the handler and emit paths: no stream identity is passed to, or checked by, any of them, while `_on_stream_exit` demonstrates the guard that is missing. The existing `test_old_stream_ending_after_a_reconnect_is_not_reported` (tests/test_data_client.py, lines 709–731) covers only the exit log of an old stream, not data delivered by one, so no test exercises this.

### 2. `alpaca_bars_window` shifts non-UTC aware bounds by wall-clock time, so DST-boundary bars are missed — UNSURE how far this reaches in production

- **Where:** `packages/canon-alpaca/src/canon_alpaca/data.py`, `alpaca_bars_window` and `start_of_day` (lines 289–308).
- **What goes wrong:** The function promises both bounds "move back one interval", and `ts_init` is defined as open plus a fixed interval (line 346, `ts_event + bar_interval_ns`). But `start - interval` and `end - interval` on a `ZoneInfo("America/New_York")` datetime do wall-clock arithmetic, which differs from a fixed 168-hour (or 24-hour) shift by one hour across a US clock change. I ran a probe (`/tmp/probe_defects.py`, via `mise exec -- uv run --locked python`):
  - `alpaca_bars_window` for a window starting at the spring weekly bar's `ts_init`, 2026-03-09 01:00 New York, returns a sent start of 2026-03-02 01:00 EST (06:00 UTC), whereas the bar's open is 2026-03-02 00:00 EST (05:00 UTC). Alpaca filters inclusively on the open, so the bar whose `ts_init` is exactly the requested start is not returned.
  - With the window ending at the autumn weekly bar's `ts_init`, 2026-11-01 23:00 New York, the sent end is 2026-10-25 23:00 EDT (03:00 UTC), before that bar's open at 2026-10-26 00:00 EDT (04:00 UTC), so the bar is missed at the end bound too.
  - The same inputs converted to UTC first are shifted correctly (sent start 05:00 UTC), which confirms the cause is the time zone of the input, not the interval.
- **Reach, stated as uncertainty:** I verified by instrumenting `alpaca_bars_window` during `test_weekly_bar_across_a_clock_change` that bounds arriving through a strategy and the engine reach `_request_bars` already converted to UTC, so the normal LiveNode path for strategy-supplied bounds is not affected. The defect is live for direct callers of the hook (the tests themselves call `_request_bars` directly, e.g. `bars_request` in tests/test_data_client.py, lines 564–575) and for the function's own contract; it also means the function's internal default start, built by `start_of_day` in New York time (line 307), is shifted by wall time while the end is shifted in UTC. I am unsure whether any production caller can present non-UTC bounds, so I rank this below defect 1.

### 3. `_disconnect` silently discards clients supplied to the constructor, so a reconnect builds real Alpaca clients instead — UNSURE whether this is intended

- **Where:** `packages/canon-alpaca/src/canon_alpaca/data.py`, `AlpacaDataClient.__init__` (lines 394–423, parameters `historical_client` and `stream`), `_disconnect` (lines 467–470) and `_connect_venue` (lines 448–453).
- **What goes wrong:** `_disconnect` sets `self._stream = None` and `self._historical = None` unconditionally. On the next `_connect`, `_connect_venue` therefore constructs fresh `StockHistoricalDataClient`/`StockDataStream` objects from environment credentials instead of reusing the ones the caller supplied. For a caller that constructed the client with its own clients, a reconnect either fails with "Alpaca paper credentials are not in the environment" (if no credentials are set) or silently starts talking through newly built real clients. The README (line 116–118) documents building a new *stream* after a timed-out disconnect, and the module header (line 71) documents dropping the REST reference because alpaca-py has no `close()`, but neither says that constructor-supplied clients are single-use.
- **How I showed it:** By reading the three functions above; the sequence is connect with supplied clients → disconnect → connect. The existing `test_old_stream_ending_after_a_reconnect_is_not_reported` (tests/test_data_client.py, lines 709–731) has to monkeypatch `StockDataStream` to get a stream back after its manual `_disconnect`/`_connect`, which is consistent with this behaviour, and it never requests bars after reconnecting, so the equivalent switch of the historical client is not exercised. I mark this unsure because the factory used in production (factories.py, lines 44–50) never supplies clients, so the impact may be limited to embedders and tests using the constructor seam.

### 4. A log-assertion test failed in the full-suite run although the expected log line was produced — the test is timing-sensitive

- **Where:** `packages/canon-alpaca/tests/test_data_client.py`, `test_one_sided_quote_count_restarts_after_resubscribing` (lines 665–680), using `logged(capfd)` (lines 181–184).
- **What goes wrong:** The test asserts that the disconnect summary `Dropped 1 one-sided Alpaca quotes for AAPL since subscribing` is present in the output captured by `capfd.readouterr()` immediately after the hosted node run returns. In my full-suite run (`mise exec -- uv run --locked pytest packages/canon-alpaca/tests -q`: 1 failed, 94 passed, 1 skipped) this assertion failed, yet the captured stdout for the same test in pytest's own report contains exactly that warning line, timestamped during the node's disconnect. So the line was written, but after `logged(capfd)` had drained the capture — the node can report itself stopped before its logged output has reached the file descriptors `capfd` reads. The same test passed when run alone, and `tests/test_data_client.py` passed as a whole (33 passed), which confirms the outcome depends on scheduling/load rather than on the code path under test.
- **Effect:** The test can fail for the wrong reason (log delivery timing), and by symmetry the other `capfd`-based assertions in the file (lines 634–662, 709–763, 801–817) can in principle pass or fail on the same timing. I am unsure of the exact buffering layer responsible (I infer an asynchronously flushed native logger from the observed ordering); the flaky failure itself is observed, not inferred.

### 5. The stream stand-in's fidelity claim is false in one respect the adapter's unsubscribe behaviour depends on, so the failed-unsubscribe test does not model alpaca-py

- **Where:** `packages/canon-alpaca/tests/conftest.py`, `FakeStream` docstring (lines 249–265), `_send` (lines 286–288), `_subscribe`/`_unsubscribe` (lines 290–301) and `run` (lines 321–328).
- **What goes wrong:** The docstring says the stand-in unsubscribes "the way `alpaca/data/live/websocket.py` does" and that "sends are made only while running". In pinned alpaca-py 0.45.0 (`DataStream._drive_run`, which I read in `.venv`), `_running` becomes true only after `_start_ws()` has connected and authenticated and the initial subscribe message has been sent; before that, `_unsubscribe` sends nothing and simply deletes handlers (raising `KeyError` for an unknown symbol), and `_subscribe` records handlers without sending. The stand-in instead sets its `running` event the moment `run()` is entered — before any connection exists — and `_send` raises `send_error` from that moment on. So in the window between the stream thread starting and alpaca-py actually connecting, the stand-in reports a send failure that real alpaca-py would not produce, and raises it at a point where real alpaca-py would silently delete the handler.
- **Sequence that shows it:** `test_failed_unsubscribe_can_be_retried` (tests/test_data_client.py, lines 372–387) waits only for `venue.stream.running.is_set()` — the stand-in's thread-entry event — then sets `send_error` and requires `_unsubscribe_quotes` to raise and keep the symbol. Against the real client in the equivalent pre-connection state, the unsubscribe would not raise at all and the adapter would drop the symbol immediately, so the retry semantics the test demonstrates are a property of the stand-in, not verified against alpaca-py. Two smaller mismatches in the same class: `_unsubscribe` appends to `self.unsubscribed` before deleting (lines 298–301), so a call that then raises `KeyError` is recorded as if a send happened; and `_serve` marks `(channel, symbol)` as sent before checking that the built message matches that symbol (lines 352–359), so a mismatched first message would permanently suppress delivery for that symbol. Neither smaller point is exercised by the current tests (all fixtures are AAPL).

### 6. `is_power_of_ten(1)` returns `True`, contradicting its own docstring — no current user-visible effect

- **Where:** `packages/canon-alpaca/src/canon_alpaca/data.py`, `is_power_of_ten` (lines 282–286).
- **What goes wrong:** The docstring says "Whether `n` is 10, 100, 1000, ...", but the loop leaves `n == 1` untouched and the function returns `n == 1`, so `is_power_of_ten(1)` is `True`. My probe printed `[True, True, True, False, False]` for `(1, 10, 100, 101, 0)`. There is no visible effect today only because the sole caller, `_emit_quote` (lines 633–642), handles `count == 1` in the preceding branch before testing `is_power_of_ten(count)`. Any future caller relying on the documented meaning would log (or act) at count 1 as well as at 10, 100, ....

### 7. A comment states the one-sided-quote count runs "since connect"; it actually runs since subscribing and is reset on unsubscribe

- **Where:** `packages/canon-alpaca/src/canon_alpaca/data.py`, line 429 (`self._one_sided_quotes: dict[str, int] = {}  # dropped per symbol since connect`).
- **What goes wrong:** The statement is false. `_unsubscribe_quotes` deletes the symbol's count (lines 504–505, commented there "counted afresh after a new subscription"), `_disconnect` clears the whole map after reporting it (lines 473–477), and the log messages themselves and the README (lines 89–93) say "since subscribing". A reader maintaining the counting or logging code from this comment would misjudge when counts reset — for example, expecting a reconnect to preserve them. Code and README agree with each other; only the comment is wrong.

### 8. `_on_stream_exit` can log "ended while subscribed" when nothing is subscribed — UNSURE

- **Where:** `packages/canon-alpaca/src/canon_alpaca/data.py`, `_on_stream_exit` (lines 679–684).
- **What goes wrong:** The guard checks only that the stream is the current one and that `_stopping` is false; it never checks `self._quote_symbols` or `self._trade_symbols`. If every subscription has been removed (so both sets are empty) and the stream then ends on its own before `_disconnect`, the client logs `Alpaca stream ended while subscribed: ...` as an error although nothing is subscribed and no delivery was expected. I did not reproduce this end-to-end (it needs a stream that ends after a full unsubscribe, which the stand-in does not produce on its own), so I report it as unsure; it follows directly from the two conditions the function tests.
