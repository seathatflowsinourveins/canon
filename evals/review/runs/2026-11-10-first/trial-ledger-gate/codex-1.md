# Review of e21935c1ada09318cdb92f929333b6295eca24c8

1. **The ledger hashes a mutable config rather than the parameters of the strategy it runs.** `src/canon_trading/ledger.py:222–241` (`record_trial`, and `trial_config`'s strategy config extraction). `MaCross` copies the trade size and bar type and constructs its moving averages in its constructor; changing its mutable config afterwards does not change those runtime values. The new recorder nevertheless hashes the changed config and runs the existing object, so its assertion that the config hashed is the config run is false. A parameter sweep that updates the config of an already constructed strategy can record runs under parameters they never used, and distinct strategies can collapse into one configuration for N or spuriously block ranking as disagreeing reruns. **Reproduced offline:** using `tests/test_ledger.py`'s `write_catalog` and `strategy`, construct the default strategy (fast 3, slow 8), set `strategy.config.fast_period = 7`, and record it; then record a fresh `strategy(fast=7)` against the same catalog and balances in the same study. The two `RecordedTrial.config_key` values are equal, but their `run.result.returns_series` dictionaries differ. Separately inspected the stale strategy: its config changes while `strategy.fast.period` remains 3. The existing key consistency check does not detect this because it rereads the same config rather than the strategy's runtime parameters.

2. **Duplicate validation omits the session calendar even though it changes the ranked returns.** `src/canon_trading/ranking.py:147–164` (`rank`, `keep` and selection of `first`). Two finished records with the same config key, start, end and raw returns are treated as equivalent even when `session_days` differs. Only the first record's calendar is then used by `daily_series`; a zero-return day can be kept or dropped, changing the common range, T, Sharpe ratios and DSR. This silently selects between contradictory inputs rather than stopping, and the result depends on record order. Catalog paths are deliberately excluded from the config key, so different catalogs or changes to the catalog can introduce this discrepancy without changing the key. **Reproduced offline:** use the three series from `tests/test_ranking.py`, replacing the pick's first return with 0.0; write two traded records for the pick with identical range and returns, one with all 30 session days and the other omitting the first day. Keep all 30 session days on the other configurations. With the full-calendar pick first, `rank` succeeds with T=30 and DSR=0.9861527922274114; reversing the two pick records also succeeds, with T=29 and DSR=0.9828867619022902. The disagreement is never reported. These were synthetic ledger records using the same Optuna attributes as the ranking tests; a real-catalog reproduction of this second defect was not run.
