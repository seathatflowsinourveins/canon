## 1. Windowed reports with `open_only=True` drop every open order submitted before the window, contradicting the stated report contract

- **File / function:** `packages/canon-alpaca/src/canon_alpaca/execution.py`, `AlpacaExecutionClient._order_status_reports` (lines 967–1008, especially the second-request condition at line 984); statements at `execution.py` lines 65–69 (module header) and `packages/canon-alpaca/README.md` line 213 (“Reports: the orders submitted in the engine's window and every open order however old”).
- **What goes wrong:** The unbounded “every open order” request is only added when `not command.open_only`. When a caller asks for open orders only *and* supplies `start`/`end`, the single request is `GetOrdersRequest(status=OPEN, after=start, until=end)`, and Alpaca filters `after`/`until` on submission time (the code's own docstring at lines 970–972 says so). A still-working order submitted before `start` is therefore absent from the result, while the module header and README promise every open order is reported regardless of age. The function's docstring (lines 970–972) does carve out the `open_only` case, so code, header and README do not agree; one of them is wrong. If NautilusTrader's periodic open-order check issues windowed `open_only=True` requests (its command type carries both fields), a long-lived GTC order falls out of every such report.
- **How I showed it:** Probe in `/tmp/test_probe_openonly.py`, reusing the checkout's stand-ins and node harness. Seeded `venue.trading.orders` with the docs' open GTC limit order (submitted 2023-12-12, `alpaca_order()` default), then called the connected client's `_generate_order_status_reports` with `SimpleNamespace(open_only=True, instrument_id=None, start=2024-01-01, end=None)`. Output: `OPEN_ONLY_REPORTS: []`, with the Alpaca queries issued being a start-up `('all', None)` followed by `('open', Timestamp('2024-01-01 …'))`. The same order with `open_only=True` and no window is reported (`OPEN_ONLY_NOWINDOW_REPORTS: ['7b08df51-…']`), isolating the window-plus-`open_only` combination as the cause.
- **Certainty:** The behaviour and the contradiction with the header/README are certain. Whether the engine's real open-check path passes a window with `open_only=True` is UNVERIFIED (native code), so the user-visible severity is unsure; at minimum the documented contract is false for this input.

## 2. (Unsure) `_reject` and `_cancel_refused` generate terminal events without re-checking order state after an `await`, so a stream event that lands first can be followed by a second, contradictory generation

- **File / functions:** `packages/canon-alpaca/src/canon_alpaca/execution.py`, `_reject` (lines 811–813), `_submit_order` (lines 633–639), `_refused` (lines 642–680), `_cancel_refused` (lines 715–742).
- **What goes wrong:** `_reject` unconditionally adds the order to `_finished` and calls `generate_order_rejected`. The stream path (`_apply`, lines 841–847) also calls `_reject`. `_refused` guards `_accepted`/`_finished` only *before* its lookup `await` (line 652); `_cancel_refused` calls `generate_order_cancel_rejected` after its lookup `await` with no check of the cached order's status or of `_finished` at all. Two interleavings follow:
  1. Submit: Alpaca's REST answer carries `status=rejected` *and* the stream delivers `rejected`. If the stream copy is processed while `_submit_order` awaits the REST call (the node loop is free during `_call`), `_submit_order` then calls `_reject` a second time for an order already rejected and in `_finished`.
  2. Cancel: a 422 cancel refusal triggers `_cancel_refused`'s lookup; while it awaits, the stream applies a `fill` (order now FILLED, in `_finished`). The lookup result (any status other than canceled/pending-cancel, including filled) still leads to `generate_order_cancel_rejected` on a filled order.
  The author clearly knew about this class of race — `_refused`'s pre-await guard and `_accept`'s re-check (lines 800–809) exist — but the post-await generation sites were not given the same re-check.
- **How I showed it:** Probe in `/tmp/test_probe_dup2.py`: the stand-in's `submit_order` was wrapped to send the fake `new`+`rejected` stream updates, sleep 0.6 s in the worker thread (so the stream rejection is applied on the node loop first), then return an order whose status is `rejected`. The node log contained 2 `OrderRejected` generations for the one order. In a separate run (`/tmp/test_probe_dup.py`, strategy self-shutting-down on the first rejection) the strategy saw a single `OrderRejected`, so whether NautilusTrader's native output drops the second generation, or the shutdown swallowed it, is unresolved — the duplicate *generation* is observed, the strategy-visible harm is not.
- **Certainty:** Unsure. Code-level double generation is demonstrated; user-visible impact depends on unverified native event validation.

## 3. (Unsure) A closed order that should be skipped with a warning can instead raise `decimal.InvalidOperation` out of `order_status_report` and fail reconciliation

- **File / functions:** `packages/canon-alpaca/src/canon_alpaca/execution.py`, `order_status_report` (lines 395–448, catch at line 445), `exact_report_price` (lines 363–368), `whole_quantity` (lines 355–360); promise at lines 67–69 (“is skipped with a warning when it is closed”) and README line 216.
- **What goes wrong:** The skip path relies on `except ValueError`. But `Decimal(str(value))` on a non-numeric or `None` value raises `decimal.InvalidOperation`, which is an `ArithmeticError`, not a `ValueError`. For a *closed* order the exception escapes `order_status_report` instead of returning `None`; `_order_report` never gets to log the skip warning, and `_logged` (lines 936–943) re-raises, failing the whole order-status report (at start-up, the node). The reachable constructions are inside the `try`, so the intent to contain them is clear — the exception type is just wrong for these inputs.
- **How I showed it:** Direct probe (`/tmp/probe1.py`) with the pinned alpaca-py models and the conftest payload: `Order(**alpaca_order(status="canceled", type="limit", order_type="limit", limit_price=None))` passed to `order_status_report(o, 0)` raises `InvalidOperation [<class 'decimal.ConversionSyntax'>]` instead of returning `None`. Controls in the same probe behave as documented: closed unmapped orders (`status` canceled/filled/expired with `type="stop"`/`"stop_limit"`) return `None`, and a closed fractional-quantity order returns `None`, so the gap is specific to Decimal conversion inputs (a limit order record with `limit_price=None`, or a non-numeric `qty`/`filled_qty`/`limit_price` string, all of which alpaca-py's model fields `str | float | None` admit).
- **Certainty:** Unsure how often Alpaca emits such a record (its documented limit-order responses carry `limit_price`); the code does not do what its header says for inputs its own input model allows.

## 4. A terminal fill that cannot be applied (no `execution_id`, or a fractional fill quantity) still marks the order finished, so any later update for that order is silently dropped

- **File / functions:** `packages/canon-alpaca/src/canon_alpaca/execution.py`, `_apply` (lines 826–866, terminal marking at lines 865–866), `_fill` (lines 868–894).
- **What goes wrong:** `_fill` returns early — logging that the fill was “not applied” — when `execution_id` is missing or `whole_quantity` rejects the fill quantity. Control returns to `_apply`, which then unconditionally executes `if event in TERMINAL_EVENTS: self._finished.add(client_order_id)`. From then on `_apply` drops *every* further update for the order at lines 836–837, including a corrected/re-sent fill carrying an `execution_id`, a `canceled`, or an `expired`. The comment at lines 56 and 879–880 says “reconciliation can infer it later”, but within a running node nothing re-runs bulk reconciliation for this order unless the engine is configured to, and the stream — the only other source — is now fenced off by `_finished`.
- **How I showed it:** Code inspection plus the existing test `test_fill_without_an_execution_id_is_logged_not_applied` (`packages/canon-alpaca/tests/test_execution_client.py` lines 423–436), which sets `venue.trading.execution_ids = False` and asserts the order remains `OrderSubmitted, OrderAccepted` with the fill logged as not applied — i.e. the terminal fill is consumed, the order never fills in the node, and (per lines 865–866) the order is in `_finished` so no later stream update can repair it.
- **Certainty:** The `_finished` marking on an unapplied fill is certain from the code. Severity is limited because Alpaca is not expected to re-send a corrected terminal fill; the residual risk is the stated “fill without an execution ID” case becoming permanently unrecoverable in-session rather than merely deferred.

## 5. `names_live_host` misses Alpaca's live host written with a trailing dot, so the paper-only check gives the wrong error (and its docstring is false) for that spelling

- **File / function:** `packages/canon-alpaca/src/canon_alpaca/execution.py`, `names_live_host` (lines 272–277) and `LIVE_HOSTS` (lines 165–173); used by `AlpacaExecutionClientConfig.__init__` (lines 245–269).
- **What goes wrong:** The check tokenises with `re.findall(r"[a-z0-9.-]+", …)` and compares whole tokens against `{"api.alpaca.markets"}`. The token for `https://api.alpaca.markets./v2` is `api.alpaca.markets.` (trailing dot retained), which is not equal to the live host, even though a trailing-dot FQDN names the same host. The docstring (“Whether `value` names one of Alpaca's live trading hosts, as a URL or a bare host name”) is therefore false for that spelling, and e.g. `AlpacaExecutionClientConfig(base_url="https://api.alpaca.markets./v2")` or a `url_override` naming that host is refused with the generic “has no setting” / “(a URL)” wording instead of the paper-only error naming the live host.
- **How I showed it:** Ran the function in the pinned environment: `names_live_host("https://api.alpaca.markets./v2")`, `names_live_host("https://api.alpaca.markets.")` and `names_live_host("api.alpaca.markets.")` all return `False`, while `https://api.alpaca.markets:443` and `API.alpaca.markets` return `True`. Confirmed `LIVE_HOSTS == {"api.alpaca.markets"}` (both `TRADING_LIVE` and `TRADING_STREAM_LIVE` in alpaca-py 0.45.0 resolve to that host).
- **Certainty:** Certain as a correctness defect of the helper. Impact is low and I state it plainly: the config fails closed anyway — any `url_override` is refused (lines 252–257) and any unknown keyword is refused (lines 266–269) — so this changes only which error is raised, not whether live trading can be reached. No input I found lets a live host through *because of* this gap.

## 6. Trade updates that are not `TradeUpdate` instances are dropped silently, unlike every REST path, which refuses raw data loudly

- **File / function:** `packages/canon-alpaca/src/canon_alpaca/execution.py`, `_on_trade_update` (lines 901–904); contrast `_submit_order` lines 631–632, `_order_status_report` lines 963–964, `_order_status_reports` lines 993–996, `_report_account` lines 580–583.
- **What goes wrong:** If the stream is built with `raw_data=True` (alpaca-py's `TradingStream` accepts it, and the client's constructor accepts an injected `stream`), alpaca-py hands the handler raw payloads. `_on_trade_update` tests `isinstance(update, TradeUpdate)` and otherwise does nothing — no log, no error — so every accept/fill/cancel for the session is silently ignored and orders sit in `SUBMITTED` with no adapter-side signal. Every other alpaca-py call site in this module raises `TypeError("alpaca-py returned raw … data; the client must use raw_data=False")` for exactly this misconfiguration, and the module's own practice (and AGENTS.md rule “No silent fallback”) is to name it. The stream seam is the one place the same condition becomes invisible.
- **How I showed it:** Code inspection: line 903 is the only handling of the `TradeUpdate | RawData` union (the type is declared at line 298), and neither branch logs. The factory path always builds `TradingStream(paper=True)` with the default `raw_data=False` (lines 545–546), so triggering this needs an injected stream — hence low severity.
- **Certainty:** Unsure whether injected-stream construction is considered in-contract (it is a public constructor parameter, also used as the test seam); the silent-drop behaviour itself is certain.
