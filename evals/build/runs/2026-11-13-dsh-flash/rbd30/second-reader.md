## Findings
1. src/canon_trading/backtest.py:250 and :316-321, src/canon_trading/ledger.py:504-514. The run config is still built with `BacktestEngineConfig(logging=logging)`, so the engine's cache keeps upstream's default `bar_capacity` of 10,000 bars per bar type (`CacheConfig().bar_capacity` printed 10000 at 2.0.0rc8). `run_backtest_config` reads the run's bars back with `Cache.bars`, and the new check `len(bars) != result.iterations` then fails every run whose sample holds more than 10,000 bars of one bar type. The starting code recorded those trials. From 26 regular sessions of one-minute bars upward, every trial is now told FAIL, failed, and a study on them can never be ranked. Two texts in the change say the opposite: the docstring at backtest.py:105-106 ("`bars` is every bar in the engine's cache, which is what the run replayed") and ADR 0041 term 3. Upstream's own setting removes the failure: `BacktestEngineConfig(cache=CacheConfig(bar_capacity=...))`, which the case's fix sizes through `keep_bars`. The report does not mention the cap. Shown by probe_bar_capacity.py: on the change, 27 sessions (10,530 bars) and 26 sessions (10,140 bars) are told FAIL, failed, with "the engine's cache holds 10000 bars and the run replayed N", while 20 sessions (7,800 bars) record COMPLETE. On the starting code, 27 sessions record COMPLETE, traded. On the change with only the engine's cache raised to 20,000, 27 sessions record COMPLETE, traded, with 10,530 cached bars. (severity: blocker)
2. src/canon_trading/backtest.py:145-163 and :218-233. The change checks that the sample is covered with interval arithmetic of its own: `_first_uncovered` and `_between_intervals` over `get_intervals`. The upstream this module names, `ParquetDataCatalog`, already provides that check as `get_missing_intervals_for_request` ("Get missing time intervals for a data request", its runtime docstring at 2.0.0rc8). The sibling module `canon_trading.bars_to_catalog` (lines 52 and 246) already calls it to find the parts a catalog does not cover, and the case's fix calls it too. This is rule 3 of `AGENTS.md`. The report's limits admit the coverage semantics are assumed ("`get_intervals` is treated as an inclusive `ts_init` coverage interval"). Shown by probe_coverage.py: on four samples, the change's own walk returns exactly the first instant of the first interval upstream's method reports missing, so it re-derives what upstream already returns. (severity: blocker)
3. src/canon_trading/backtest.py:222-233, with the module header at :25-27, the `backtest_run_config` docstring at :194-197 and docs/adr/0041-trial-ledger-sample-and-data-identity.md:41-43. The refusal names one instant, not the missing part, its end or any later part. For a gap between two loads, its only remedy is `consolidate_data`; it never says to load the range. The header, the docstring and ADR 0041 term 1 say a gap between intervals "is closed by" consolidation, but leave out the statement's condition that a load showed the stretch to hold no bar. Consolidation marks a never-loaded stretch as covered, so following the message lets a fragment of the sample pass, which is the outcome defect 2 is about. Shown by probe_consolidate_hint.py: the catalog has three loads with two never-loaded weeks of weekday sessions between them. The change refuses with "missing 2025-03-23T00:00:00.000000001+00:00 ...; a stretch a load recorded with no bar is closed by consolidating the catalog", whereas upstream reports two missing ranges with their ends (probe_coverage.py). After `consolidate_data`, the trial records COMPLETE with 30 session days of the sample's 40 weekdays. (severity: fix)
## Per-defect check

The digest should be of the bars the run read. A run whose bars cannot all be accounted for, or that read a bar outside the sample, should be told failed": removed. Checked three ways. `test_the_digest_is_of_the_bars_the_run_read_not_a_later_catalog` and both cases of `test_bars_the_cache_does_not_account_for_are_told_failed` pass on the change and fail on the starting code. This holds only up to 10,000 bars per bar type; above that, every run is told failed (finding 1).
2. "Any overlap of the catalog with the sample is accepted, so two configurations pass on a fragment of the sample. A run should need the sample covered in full: a part that is missing is refused before a trial is asked for, and named, and so is a sample the catalog does not reach at all. A stretch that a load showed to hold no bar can be closed by consolidating the catalog": removed for a sample with both bounds, which is the only path the ledger takes. The two cases of `test_a_sample_the_catalog_covers_in_part_is_refused_naming_the_gap`, `test_a_sample_the_catalog_does_not_reach_is_refused_before_a_trial` and `test_a_hole_no_load_can_fill_is_closed_by_consolidating_the_catalog` pass on the change and fail on the starting code. In probe_consolidate_hint.py, the starting code records a trial on a sample with two never-loaded weeks, while the change refuses it before any trial exists. The part is named only by its first instant (finding 3).
3. "A keyed record that failed before its sample number was written is left out of the ranking, instead of stopping it until a later record of its key resolves it.
