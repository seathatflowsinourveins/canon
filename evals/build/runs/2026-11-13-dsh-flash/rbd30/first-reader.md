# First reader: rbd30
Mark: no
Blocker: 4. The change tells every trial over more than 10,000 bars of one bar type FAIL, where the starting code recorded it, because it reads the run's bars from an engine cache it leaves at upstream's default `bar_capacity` of 10,000 and then requires one cached bar per iteration, shown by 26 regular sessions of one-minute AAPL bars (10,140 bars) recorded with `record_trial`: COMPLETE/traded with 26 session days on the starting code, FAIL/failed with "the engine's cache holds 10000 bars and the run replayed 10140" and no digest on the change.

## Findings
1. src/canon_trading/ledger.py:504-509, with src/canon_trading/backtest.py:250 and :315-321 (review finding 1). The run's bars are read with `Cache.bars`, which keeps at most `CacheConfig.bar_capacity` bars per bar type. That is 10,000 by default at the pin: `CacheConfig().bar_capacity` prints 10000 in the copy's install, and the pinned source has `crates/common/src/cache/config.rs:73-76` and `mod.rs:2473-2477`. `backtest_run_config` still builds `BacktestEngineConfig(logging=logging)` with no cache config, so the new check `len(bars) != result.iterations` tells every trial with more than 10,000 bars of one bar type FAIL/failed. Nothing lets such a trial be recorded, so a study on such a sample can never be ranked; the starting code recorded it. The suite runs at most 70 bars. Several texts are untrue past that count: the docstring saying `bars` "is what the run replayed" (backtest.py:105-106), the ledger header (ledger.py:42-48) and ADR 0041 term 3's new text. The report's limits do not mention the cap. Shown by `probes/probe_capacity.py`. On the change, 9,750 one-minute bars record as COMPLETE/traded, and 10,140 bars raise "the engine's cache holds 10000 bars and the run replayed 10140" (trial FAIL/failed, no digest). On the starting code the same 10,140 bars record as COMPLETE/traded with 26 session days and a digest. ADR 0048's pre-registered daily study, about 1,370 bars per symbol, is under the cap. The adapter also serves MINUTE and HOUR bars (bars_to_catalog.py header), and the ledger takes any of them. (severity: blocker)
2. src/canon_trading/backtest.py:145-163, used at :221-233 (review finding 7). `_first_uncovered` and `_between_intervals` are a hand-written interval-gap finder over `get_intervals`. The upstream the module already uses, NautilusTrader's `ParquetDataCatalog`, provides `get_missing_intervals_for_request(start, end, data_type, identifier)`. It is in the installed `persistence/__init__.pyi:387`, with the docstring "Get missing time intervals for a data request". The same package already calls it for the same question (src/canon_trading/bars_to_catalog.py:52 and :246). AGENTS.md rule 3 ("Glue yes, invention no"). Shown by `probes/probe_coverage.py`, on seven catalogs:
   - the whole window;
   - a year short at the end;
   - a year short at the start;
   - a hole between two loads;
   - two adjacent loads;
   - bars written with no window;
   - a sample past the catalog.

   On every one, upstream's call gives the same first missing instant as `_first_uncovered`, and it also gives every missing part with its end. The change's message names only the first instant. Neither the report nor the module header names the upstream call. (severity: blocker)

## Review findings not taken
1. src/canon_trading/ledger.py:422 (the cache replaces a time bar with an equal `ts_event` and skips an older one, so the equality with `iterations` rejects valid runs): the cache behaviour holds. I read the pinned `crates/common/src/cache/mod.rs:7140-7157` but did not run it. It needs a catalog holding two bars of one bar type with one `ts_event`, or bars whose `ts_event` order differs from their `ts_init` order, and no source shows this repository making one. `parse_bar` stamps `ts_init` one interval after `ts_event` (packages/canon-alpaca/src/canon_alpaca/data.py:371-383). The repository's loader fetches only parts the catalog does not cover (bars_to_catalog.py header). Were it to happen, telling the run failed is what the statement asks for "a run whose bars cannot all be accounted for". The case's fix has the same equality check.
2. src/canon_trading/ranking.py:228 (`variant_study._to_record` never re-runs a key whose sample write failed after it ran, so the ranking stops for good): this holds only in part. `probes/probe_variant_pass.py` sequence A is the review's: a direct `record_trial` of a key that already ran, failing at its `sample` write. There `rank` stops and `record_grid` does not re-run the key, but a later `record_trial` of the key resolves it (N = 2). That is the statement's rule: "stopping it until a later record of its key resolves it". In the tool's own passes (sequence B), such a record is made only for a key whose latest record on the sample did not run, so the next pass re-runs the key and the ranking passes. The stop itself is what defect 3 requires.
3. src/canon_trading/returns_matrix.py:100 (NautilusTrader's daily series ends at the last account event, so a trial whose last fill precedes the last session day is refused): not taken. Refusing a session day with no return is what defect 5 asks ("Such a day should be refused, and named"), whatever leaves the day without a return, and the case's fix refuses it the same way. The premise is UNVERIFIED (see Declined to judge).
4. src/canon_trading/backtest.py:236 (a sample starting at midnight over a catalog written with no window is refused): this holds, as `probes/probe_coverage.py` case f shows. It is the full coverage the statement asks for. NautilusTrader's own `get_missing_intervals_for_request` reports the same gap on that catalog. The repository's loader records the window it asked for (bars_to_catalog.py header; `tests/conftest.py` `write`), so a sample over a loaded window is covered (case a).
5. src/canon_trading/ranking.py:199 (a record that did not run, with a sample number the study does not have, stops the ranking with nothing to clear it): this needs a `sample` attribute that is not one of the study's sample numbers, and no source writes one. `record_trial` writes the current sample's number (ledger.py:500). Numbers are ints from `samples()` (ledger.py:259-262), and samples are only appended (`move_sample`, ledger.py:293-295). The report says a failing record with such a number "is named too", which is what the code does.
6. src/canon_trading/ledger.py:335 (a study with no sample made by a non-ledger writer, with trials or another direction, is adopted): this needs a study in the ledger made by another writer, and no source shows one. `create_ledger_study` is the only creator, always with `direction="maximize"`. `record_trial` reads the current sample (ledger.py:477) before `study.ask()` (ledger.py:496), so a study with no sample cannot hold a trial. A grep of `src`, `packages` and `scripts` finds no other `create_study`, `ask`, `enqueue_trial` or `add_trial`.
7. src/canon_trading/backtest.py:228 (the intervals are sorted twice): this is true (backtest.py:218 and :148) but changes no behaviour. It sits in the helper of Finding 2, whose remedy removes it.
8. src/canon_trading/backtest.py:322 (every bar is kept alive in `RecordedTrial.run`, so memory grows with trials times bars): `record_grid` keeps only each trial's number (variant_study.py:192), not the `RecordedTrial`. `list(run.bars)` copies references, not bars, and in this change the cache caps the list at 10,000 per bar type.

## Per-defect check
1. "The data digest and the session days of a run are read from the catalog after the replay ... The digest should be of the bars the run read. A run whose bars cannot all be accounted for, or that read a bar outside the sample, should be told failed": removed. The digest and session days come from the cache's bars (ledger.py:504-522), with the count and range checks (ledger.py:505-514). `test_the_digest_is_of_the_bars_the_run_read_not_a_later_catalog` and both cases of `test_bars_the_cache_does_not_account_for_are_told_failed` pass on the change and fail on the starting code. Past 10,000 bars of one bar type every run is told failed (Finding 1).
2. "Any overlap of the catalog with the sample is accepted ... A run should need the sample covered in full: a part that is missing is refused before a trial is asked for, and named, and so is a sample the catalog does not reach at all. A stretch that a load showed to hold no bar can be closed by consolidating the catalog": removed for every run given both bounds, which is every ledger run. The check is backtest.py:221-233, reached before `study.ask()` at ledger.py:496. Four graded tests pass on the change and fail on the starting code: both cases of the partial-coverage test, the unreached-sample test and the consolidation test. `probes/probe_coverage.py` refuses cases b, c, d, f and g, and accepts a and e. Only the first missing instant is named (Finding 2).
3. "A keyed record that failed before its sample number was written is left out of the ranking, instead of stopping it until a later record of its key resolves it. A record that ran to the end with no sample number of the study should stop the ranking too, named": removed. `test_a_keyed_failure_before_its_sample_is_written_stops_the_ranking` and the three cases of `test_a_record_that_ran_with_no_sample_number_of_the_study_stops` pass on the change and fail on the starting code. In `probes/probe_variant_pass.py` sequence A, step 2, the starting code ranks N = 2 past the failed record. The change stops on it, naming it, until step 4's later record.
4. "A creation interrupted between the study's name and its sample leaves a name that can be neither opened nor created again": removed (ledger.py:194-202, 265-273). `test_a_creation_interrupted_before_its_sample_is_completed_by_the_next` passes on the change and fails on the starting code.
5. "A session day with no return in a trial's series is dropped from the calendar ... Such a day should be refused, and named": removed (returns_matrix.py:100-106). `test_a_session_day_with_no_return_is_refused` and `test_session_days_with_no_return_stop_and_are_named` pass on the change and fail on the starting code.
