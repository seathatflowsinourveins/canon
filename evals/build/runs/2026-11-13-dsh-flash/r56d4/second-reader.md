# Second reader: r56d4
Mark: no
Blocker: 4. Once one modify's replacement has been applied, a `canceled` or `expired` update for the next replacement (the order then live at Alpaca) that arrives before that replacement's `replaced` is dropped as a "superseded order" at `packages/canon-alpaca/src/canon_alpaca/execution.py:1520-1527`, so the node's order never closes, and a `replaced` that comes later moves it onto the ended order and leaves it open, shown by two price modifies in a row with the second's `replaced` held back or never sent and the second replacement then canceled or expired at Alpaca, or by the node's own cancel answered 422 on the first replacement and sent on to the second (probes A and A2: the starting code and the case's fix end the order, the change does not).
## Findings
1. `packages/canon-alpaca/src/canon_alpaca/execution.py:1520-1527`. The superseded check drops a `canceled` or `expired` update for any order other than the one last adopted, without asking which way the replace chain runs, so a newer replacement's update returns before `_adopt_if_live` (1545-1549), which follows the chain forward for fills through `_replaces_chain_contains`; the live order's cancel or expiry is lost, and a later `replaced` moves the node's order onto the ended order (`OrderUpdated`) and leaves it open. This also contradicts the report ("A replacement's fill, cancel or expiry arriving before `replaced` now adopts the replacement's terms first (`_adopt_if_live`). It will move forward through a chain of replacements") and the module header at 24-25, so it is blocker 5 as well. Shown by probes A (all four cases) and A2: on the change the events end `OrderUpdated, OrderPendingUpdate` (`replaced` never sent) or `OrderPendingUpdate, OrderUpdated` (`replaced` late), with the log "Alpaca canceled of superseded order <second replacement> for <node order> is ignored; the node's order is its replacement"; the starting code and the case's fix end the order with `OrderCanceled` or `OrderExpired`. No periodic check closes it before the node next starts: `LiveExecutionEngineConfig.open_check_interval_secs` defaults to `None` in the NautilusTrader the copy's lock installs (`nautilus_trader/live/__init__.pyi:748`), and nothing under `src/` or `packages/canon-alpaca/src/` sets it (grep). (severity: blocker)
2. `packages/canon-alpaca/src/canon_alpaca/execution.py:1682-1684`, with 1185-1186 and 1206-1208. `_adopt` adds the replaced order's ID to `_settled_modifies`, the key `_begin_modify` had cleared for a second modify sent to that same order; when the first modify's `replaced` is applied while the second's PATCH is in flight, Alpaca's 422 "order already replaced" reaches `_modify_rejected`, finds the key settled and returns, so the second modify gets no `OrderModifyRejected` and the strategy cannot tell it failed. Shown by probe B: with a second price the first replacement does not hold (other-price) the starting code gives `OrderModifyRejected` and the change gives none, a regression; with the statement's terms (case-terms) both give none. The case's fix fails both cases as well. (severity: blocker)
3. `packages/canon-alpaca/src/canon_alpaca/execution.py:2053-2056` and 1640-1643. `except APIError, OSError: return False`, with nothing logged. In `_replacement_took_over`, a failed read of the old order makes `_order_report` (2011-2021) drop a closed replacement, so a reconciliation that meets one failed read loses the node's filled replacement, the defect-1 outcome, with no message; the docstring (2046) states the fallback, but nothing at run time says it happened. In `_replaces_chain_contains`, a failed read makes `_adopt_if_live` skip adoption, so a newer replacement's fill is applied under the older terms (the overfill of defect 4), again with no message. The module's other failed reads log, raise or treat only a 404 as an answer (for example 1576-1584, 1776-1779, 2007-2009). Shown by probe C (HTTP 500 on the old order's read: on the change no report for the node's order and the failure not logged; the case's fix reports it `FILLED` without that read) and, for 1640-1643, by reading. (severity: blocker)
4. `packages/canon-alpaca/src/canon_alpaca/execution.py:792`, 862, 1185, 1190-1191. `_modifying` is written and cleared but never read for a decision (those are all its uses); `_settled_modifies` makes every decision, and `_modifying` only keeps the named test's inspection at `packages/canon-alpaca/tests/test_execution_client.py:1452` (`strategy.client_order_id not in client._modifying.values()`) true. The starting code has no `_modifying`; the case's fix reads its own to decide (`_settle_modify(target)` returns whether a modify was awaiting). A review round would keep one record and remove the other. Shown by grep of every use. Not counted as blocker 1: the defect that test names is removed by the log and settle at 1486-1501. (severity: fix)
5. `packages/canon-alpaca/src/canon_alpaca/execution.py:787-793` (written at 1209, 1252, 1497, 1499, 1587, 1590, 1679, 1680, 1684; cleared only on disconnect, 860-863). `_adopted`, `_handled_replacements` and `_settled_modifies` are never pruned when an order ends, so every modify leaves IDs for the whole session: defect 9's build-up moved from answers to IDs. Shown by probe D: after four modifies and a fill the change keeps 1, 4 and 4 entries (and 0 answers); the case's fix keeps 0 in `_adopted` and `_answers`. The starting code's `_replacements` and `_finished` are also kept for the session, so this is the same pattern, not a new kind. (severity: fix)
6. `packages/canon-alpaca/src/canon_alpaca/execution.py:31-32` (header text the change added), with 1472-1483 and 1502-1510. When a replacement's `rejected` and the old order's `order_replace_rejected` both arrive for one modify, they are keyed by different orders (the replacement's ID, the old order's ID), so the node gets two `OrderModifyRejected`, contrary to the header's "once per modify however many of Alpaca's answers report it" and the report's "`_modify_rejected` emits at most one `OrderModifyRejected` per attempt". Shown by probe E: two on the change and on the starting code, in either order; one on the case's fix. Not a regression; the report's sentence goes on to name the HTTP-or-stream pair, and whether Alpaca sends both is UNVERIFIED, so not counted as blocker 5. (severity: fix)
## Per-defect check
1. When the `replaced` update never reaches the client and the replacement then fills, reconciliation reports neither the replacement nor the old order, so the node's order is never reported filled and its fill is lost: removed. `_order_report` (2011-2021) reports a closed replacement whose old order reads `replaced` (`_replacement_took_over`, 2038-2057); `test_filled_replacement_is_reported_when_replaced_was_missed` passes in the copy. If that read fails the fill is still lost, now silently (finding 3, probe C).
2. A replace that Alpaca refuses on the HTTP answer and again with an `order_replace_rejected` update gives two `OrderModifyRejected` events for one modify: removed. Both answers name the targeted order, and `_modify_rejected` (1206-1211) reports it once in either order; `test_replace_rejected_twice_over_is_one_modify_rejection` passes. A replacement's `rejected` with `order_replace_rejected` still gives two (finding 6, probe E).
3. A `replaced` update delivered twice gives two `OrderUpdated` events: removed. `_already_adopted` (1651-1656) is checked at 1591; `test_replaced_delivered_twice_is_one_update` passes.
4. A fill on the replacement that arrives before `replaced` is applied to the node's order under the old terms: a fill larger than the old quantity is dropped as an overfill, and the order takes the replacement's terms only after the fill: removed. `_adopt_if_live` (1545-1549) runs before `_accept` and `_fill`, and follows the chain forward for a newer replacement; both cases of `test_fill_on_a_replacement_before_its_replaced_applies_the_replacement_first` pass. A failed chain read skips this silently (finding 3).
5. A `canceled` or `expired` update for the old order, arriving after it was replaced, closes the node's order while its replacement still works at Alpaca: removed. Such an update carrying `replaced_by` is followed (1514-1519), and one for an order other than the adopted replacement is ignored (1520-1527); `test_late_cancel_of_the_replaced_order_does_not_cancel_the_replacement` passes. The same check also drops a newer replacement's update (finding 1, probes A and A2).
6. `pending_replace` is not a status the client maps, so an open order that is mid-replace fails start-up reconciliation; one that has fills should be reported partly filled: removed. Line 320 maps it to `ACCEPTED` and 632-634 to `PARTIALLY_FILLED` with fills; `test_open_order_pending_replace_at_startup_is_reported` and `test_pending_replace_with_fills_is_reported_partly_filled` pass.
7. When the replacement read at `replaced` is itself pending replace, or already replaced again, the client raises and generates no `OrderUpdated` instead of following it to the live order: removed. `_live_order` (1596-1613) follows `replaced_by` to the order Alpaca holds, and `pending_replace` maps; both cases of `test_replaced_whose_replacement_has_moved_on_still_updates` pass.
8. A second modify sent before the first's `replaced`, and refused by Alpaca, is taken for alpaca-py's retry of the first when the first replacement already holds the terms it asked for, so it gets no `OrderModifyRejected`: removed. `replaces_as_asked` (554-583) fills a term the request left out from the replaced order, so the first replacement's quantity no longer passes for the second request's unchanged one; `test_second_modify_refused_after_the_first_replaced_is_rejected` passes. If the first's `replaced` is applied while the second is in flight, the second still gets no `OrderModifyRejected`, now through `_settled_modifies` rather than the retry check (finding 2, probe B case-terms), as on the case's fix.
9. A PATCH answer that arrives after its `replaced` was applied is stored and never removed, so answers build up for the whole session: removed. 1171-1181 keeps an answer only while its replacement is unhandled, its target unsettled and the order unfinished; `test_answer_after_replaced_is_not_kept` passes, and probe D leaves 0 answers (3 on the starting code). IDs are kept instead (finding 5).
10. When the old order fills before Alpaca rejects its replacement, the client returns before the branch written for that case, so nothing says what became of the modify: removed. The branch (1486-1501) now runs before the `_finished` guard (1511-1512), logs "which had filled first; the fill is the outcome" (1492-1495) and settles; `test_rejected_replacement_after_the_old_order_filled_settles_the_modify` passes.
