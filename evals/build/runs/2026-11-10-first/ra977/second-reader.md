## Findings
1. src/canon_trading/ranking.py:35-37, 313: the header says `astimezone(UTC)` "converts that local time back to UTC". That is not true during the local fall-back hour. Optuna 5.0.0 (`storages/_rdb/models.py:193-201`, installed copy) builds `datetime_start` as `utc.replace(tzinfo=utc).astimezone().replace(tzinfo=None)`, and that drops `fold`. So two UTC instants an hour apart come back as the same naive local time, and `astimezone(UTC)` (fold=0) maps both to the earlier one. Evidence: with TZ=America/New_York, a stored 2026-11-01T06:30 UTC becomes local 01:30 and then 2026-11-01T05:30:00+00:00, one hour early, the same result as a stored 05:30. A trial started in that hour gets its recorded range wrong by an hour, and the earliest or latest trial can be misidentified. The loss comes from Optuna's naive-local API, and the public API offers nothing better, so the code is acceptable. But the header states an exact conversion, and rule 4 asks for the limit to be labelled. A review would have had it say so. (severity: fix)
2. src/canon_trading/ranking.py:136-141: the `_ran` docstring still says a traded record is told `FAIL` only "because its own Sharpe ratio is not finite". After this change the ledger also tells `FAIL` (still `traded`) for a series that `daily_series` rejects (ledger.py `_session_sharpe`, `record_trial` docstring). The gate's handling is still correct, because `rank` re-runs `daily_series` on that record and stops with the reason. But the docstring in a file this change edits now leaves out one of the two causes. (severity: fix)
