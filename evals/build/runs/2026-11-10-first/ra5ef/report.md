# Report

## What was wrong

1. **Cancel-all skipped `PENDING_CANCEL`.** In `AlpacaExecutionClient._cancel_all_orders` (`packages/canon-alpaca/src/canon_alpaca/execution.py`), each selected order was re-read at its turn and skipped when `order.status == OrderStatus.PENDING_CANCEL`. A cancel that got no answer (e.g. a read timeout, handled in `_cancel` by logging "got no answer; the order is left as it is") leaves the node's order `PENDING_CANCEL` — NautilusTrader generates `OrderPendingCancel` when the cancel command is sent — while the order still works at Alpaca. A later cancel-all therefore never re-sent the cancel and the order stayed working.

2. **Tracing an order with a client order ID NautilusTrader cannot hold raised outside the skip/fail handling.** `ClientOrderId(value)` raises `ValueError: invalid string …` for an empty or non-ASCII value (verified this session against the pinned NautilusTrader: `''` → "was empty", `'订单-1'` → "contained a non-ASCII char"), as an order made outside the node (e.g. Alpaca's dashboard) can carry. `order_status_report` already contained that raise inside its `try`, returning `None` for a closed order it cannot map and re-raising as `Alpaca order {id} ({symbol}) is open with …` for an open one. But the tracing that runs before it — `_root_id` (for the mass-status reports in `_order_report`) and `_node_order_id` (for trade updates) — constructed `ClientOrderId(alpaca_order.client_order_id)` and `ClientOrderId(prior.client_order_id)` unguarded. One closed order with an unholdable ID therefore raised out of `_generate_order_status_reports` and aborted the whole mass status, and with it start-up reconciliation, instead of being skipped; an open one raised without the "is open with invalid string" reason that names it; and a valid replacement of such an order raised while walking its `replaces` chain instead of being reported under its own ID.

## What I changed, and why that way

All changes are in `packages/canon-alpaca/src/canon_alpaca/execution.py`, plus the comments/records the change made untrue (below). No dependency was added and no test file was edited.

- **Cancel-all no longer skips `PENDING_CANCEL`.** The re-read at each order's turn now skips only a missing or closed order (`if order is None or order.is_closed: continue`), so a pending-cancel order is canceled again by ID through the same `_cancel_logged` path as every other order. This is the smallest change that removes the defect: it reuses the existing per-order cancel handling, including `_cancel_refused`, which already generates nothing when Alpaca shows the order canceled or pending cancel (the alpaca-py retry case), so re-sending a cancel that did in fact reach Alpaca does not produce a spurious rejection.

- **New helper `holdable_client_order_id(value) -> ClientOrderId | None`** next to the other Alpaca-to-Nautilus converters: it returns `ClientOrderId(value)`, or `None` when that raises `ValueError`. Its docstring names the contract it follows (below).
- **`_root_id` now returns `ClientOrderId | None`.** It returns `None` when the order's own client order ID is unholdable, and while walking `replaces` links it stops at a prior order whose ID is unholdable (`prior_id is None: break`) instead of raising or tracing past it — so a valid replacement keeps its own ID as the root. Results are still cached under the raw Alpaca string, as before.
- **`_order_report` needed no new handling:** with `_root_id` returning `None` for an unholdable own ID, it already passes `renamed=None` into `order_status_report`, where `ClientOrderId(order.client_order_id)` raises inside that function's existing `try` — a closed order returns `None` and is skipped with the `_order_report` warning, and an open order raises `Alpaca order {id} ({symbol}) is open with invalid string …`, which `logged_failure` logs before the mass status fails. That is exactly the behaviour the tests name, reached by removing the premature raise rather than by adding a parallel path.
- **`_node_order_id` uses the same helper** and returns `None` for an unholdable own ID, so a trade update for such an order is dropped with the existing "which this node does not hold" log line instead of raising in `_apply_trade_update`. Its `root` check now also guards `root is not None`.
- **The `_order_report` skip warning** now lists "client order ID" among the unmappable fields, so the warning for a skipped closed order is true for this case too.

## Which upstream API or contract the change follows

- **NautilusTrader's `ClientOrderId`** (pinned NautilusTrader v2.0.0rc8, named in the module header): it refuses an empty or non-ASCII value with `ValueError: invalid string …` (verified this session, quoted above). The adapter cannot invent an ID for such an order, so an unholdable ID is treated as "an order this slice does not map" — the existing contract of `order_status_report` (closed → skipped with a warning, open → fail the report by name), which traces to the reconciliation concept page cited in the module header: start-up fails on an open order this slice cannot represent rather than leaving a working order unknown to the node.
- **Cancel-all selection follows upstream's own adapters**, as the module header and ADR 0036 already cite: Kraken spot selects the matching open orders from the cache and cancels them by explicit venue ID (its venue cancel-all is account-wide, as Alpaca's "Delete All Orders" is here, so that endpoint is still not called), and — per the reproducing test's stated basis, which ADR 0036 and the `_cancel_all_orders` docstring now record — Kraken spot, Binance spot, Bybit and Interactive Brokers include every open order, a `PENDING_CANCEL` one included. Alpaca's "Delete Order by ID" (204, or 422 when no longer cancelable) is still the per-order endpoint used, unchanged.

## Anything I am unsure of

- The claim that upstream's Kraken spot, Binance spot, Bybit and Interactive Brokers cancel-all paths include every open order (including pending-cancel) is taken from the reproducing test's comment and is now recorded in the code and ADR 0036 on that basis; I did not re-read those upstream adapters this session, so that attribution is **UNVERIFIED** beyond the test's statement. The behavioural reason stands on this repo's own evidence: a no-answer cancel leaves the order pending cancel locally while it works at Alpaca, and `_cancel_refused` already absorbs a redundant cancel Alpaca shows as pending cancel.
- What Alpaca answers a second cancel of an order already pending cancel at Alpaca (as opposed to locally) is not documented on the pages this repo cites (**UNVERIFIED**); the code path treats a 422 through the existing lookup, which generates nothing if Alpaca shows the order canceled or pending cancel.
- Alpaca orders whose `client_order_id` is missing/`None` were not special-cased: alpaca-py's `Order` model builds that field as a string, so such an answer fails earlier as an unparsable answer, outside this change.
